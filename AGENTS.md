# Инструкции для работы с RouteCraft

RouteCraft — проект декларативной маршрутизации OpenWrt. Разработка начата: текущие возможности и результаты проверок перечислены в `README.md` и `docs/development-journal.md`; наличие документации само по себе не означает готовности продукта.

Начинайте с `README.md`, `docs/install.md`, `docs/developers.md` и актуальных требований. `docs/execplan.md` описывает завершённую подготовку; прежний `docs/development-execplan.md` заблокирован пользователем до отдельного разрешения после коррекции. При расхождениях действуют прямые указания пользователя, затем актуальный план PoC. Исходные документы находятся в игнорируемом локальном `archive/source-handoff/` и не гарантированно доступны из Git.

Целевая политика обрабатывается сверху вниз, первое совпадение побеждает, фильтры внутри правила объединены ИЛИ, последнее правило — default. Не подменяйте отсутствующие категории пустыми наборами; не переключайте недоступный VPN на direct без явной политики. VLESS provider, обновление геоданных и apply не должны конкурировать за запись единой активной конфигурации. Для изменений сети проектируйте идемпотентность и проверяемый откат.

Не фиксируйте тестовые IP, учётные данные, подписки и приватные hostnames в документации или CI. Текущие частные параметры тестового контура сохранены локально в игнорируемом `archive/private-test-environment.md`. Не изменяйте пользовательское оборудование без отдельного согласования. Не предполагайте установленные версии программ или доступность стендов без проверки.

`top50-gw` (`192.168.80.253`) и `kv256-gw` (`192.168.64.253`) — production OpenWrt hosts. Не подключайтесь к ним, не сканируйте, не диагностируйте и не меняйте их без прямого запроса пользователя на конкретное действие; такое разрешение распространяется только на указанный объём, без сопутствующей настройки.

При разработке обновляйте `docs/poc-execplan.md`, фиксируйте решения и доказательства. Проверяйте реальное поведение трафика, а не только синтаксис JSON или статус процесса. Заявляйте только реально проверенные функции; тестовые заглушки и настоящие Tailscale/VLESS интеграции указывайте отдельно.

Делите объёмную работу на этапы и после каждого этапа разработки и тестирования каждой подзадачи кратко записывайте в `docs/development-journal.md`: что сделано, результат тестов и вывод. Предпочитайте простую реализацию поверх штатных возможностей sing-box. Добавляйте сложность только при обоснованной необходимости и записывайте причину в журнал.

Для разработки и тестирования по возможности используйте предоставленные VM; не запускайте локальный Python без необходимости. Поддерживайте краткий архитектурный обзор `docs/overview.md` в соответствии с реальным состоянием продукта.

### Изолированный тестовый стенд

Если пользователь явно обозначил VM как изолированный тестовый стенд и разрешил настройку, WAN-side управление (включая SSH и ping, когда они нужны для работы стенда) разрешено. Не блокируйте его по умолчанию и не отключайте firewall вместо настройки нужных правил; оставляйте рабочими необходимые для стенда forwarding, NAT и DNAT. Это правило относится только к явно указанным тестовым VM и не расширяет доступ к production-узлам или пользовательскому оборудованию.
