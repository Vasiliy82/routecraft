# Инструкции для работы с RouteCraft

RouteCraft — проект декларативной маршрутизации OpenWrt. Разработка начата: текущие возможности и результаты проверок перечислены в `README.md` и `docs/development-journal.md`; наличие документации само по себе не означает готовности продукта.

Начинайте с `README.md`, `docs/test-environment.md` и `docs/poc-execplan.md`. `docs/execplan.md` описывает завершённую подготовку; прежний `docs/development-execplan.md` заблокирован пользователем до отдельного разрешения после коррекции. При расхождениях действуют прямые указания пользователя, затем актуальный план PoC. Исходные документы находятся в игнорируемом локальном `archive/source-handoff/` и не гарантированно доступны из Git.

Целевая политика обрабатывается сверху вниз, первое совпадение побеждает, фильтры внутри правила объединены ИЛИ, последнее правило — default. Не подменяйте отсутствующие категории пустыми наборами; не переключайте недоступный VPN на direct без явной политики. VLESS provider, обновление геоданных и apply не должны конкурировать за запись единой активной конфигурации. Для изменений сети проектируйте идемпотентность и проверяемый откат.

Тестовые VM и тестовые учётные данные приведены в `docs/test-environment.md`; пользователь разрешил хранить их в репозитории. Не путайте VM1/VM2 с историческим TOP50 `.253`: его нельзя изменять без отдельного согласования. Не отправляйте тестовые подписки и ключи в публичные журналы или CI без необходимости. Не предполагайте установленные версии программ или доступность стендов без проверки.

При разработке обновляйте `docs/poc-execplan.md`, фиксируйте решения и доказательства. Проверяйте реальное поведение трафика, а не только синтаксис JSON или статус процесса. Заявляйте только реально проверенные функции; тестовые заглушки и настоящие Tailscale/VLESS интеграции указывайте отдельно.

Делите объёмную работу на этапы и после каждого этапа разработки и тестирования каждой подзадачи кратко записывайте в `docs/development-journal.md`: что сделано, результат тестов и вывод. Предпочитайте простую реализацию поверх штатных возможностей sing-box. Добавляйте сложность только при обоснованной необходимости и записывайте причину в журнал.

Для разработки и тестирования по возможности используйте предоставленные VM; не запускайте локальный Python без необходимости. Поддерживайте краткий архитектурный обзор `docs/overview.md` в соответствии с реальным состоянием продукта.
