# Журнал разработки RouteCraft

Каждая запись кратко фиксирует работу, проверку и вывод. Реальные сетевые проверки и проверки конфигурации указываются раздельно.

## 2026-11-25 — сжатие и целостность в snapshotctl 0.2.1

- Новый снимок хранится как gzip-образ и SHA-256 в одном каталоге. При сбое копирования временный каталог удаляется. Перед восстановлением проверяются SHA-256, gzip-поток и распакованный размер. Сырые файлы 0.2.0 остаются на диске.
- Локально проверены сжатие и побайтовое восстановление на тестовом файле, отказ без записи и перезагрузки при неверной сумме, ошибке gzip и неверном размере, а также отсутствие опубликованного снимка при ошибке чтения. На R28S версия 0.2.1 пока не устанавливалась.

## 2026-11-25 — проверка snapshotctl 0.2.0 на NanoPi

- На FriendlyWrt отсутствует `blockdev`. Размер раздела берётся из sysfs. После обновления создан снимок размером 1 610 612 736 байт с правами `0600`. `snapshotctl list` показывает снимок, справка показывает версию.
- Повторная установка заменила оба скрипта. На роутере `recover` вернул удалённую ссылку и подтвердил автомонтирование. CLI отклонил короткий тестовый образ и удалил его по команде. Полный снимок остался на диске, роутер продолжил работать без перезагрузки. Factory Reset не выполнялся.
- В файловой имитации проверены запись через `dd`, перезагрузка через заглушку и отказ образу неверного размера.

## 2026-11-25 — установка менеджера снапшотов одной командой

- Реализация. `snapshot/setup.sh` принимает запуск через stdin, монтирует `opt` и создаёт на нём оба скрипта. Режим `recover` возвращает UCI и ссылку после сброса из существующей установки. В справке CLI три операции.
- Проверка. Локальная имитация прошла установку через pipe, восстановление после удаления монтирования и ссылки, побайтный откат с заглушкой перезагрузки и удаление. Режим `recover` сохранил скрипты и снимок. Роутер не изменялся.

## 2026-11-25 — упрощение снапшотов FriendlyWrt

- Решение. По уточнению пользователя удалены Go-компоненты и интеграция с initramfs. Три shell-скрипта монтируют `opt`, возвращают UCI после сброса и работают с сырыми образами. Откат выполняет `dd conv=fsync` в активный `userdata` и сразу вызывает `reboot -f`. Риск несогласованности ext4 описан в руководстве.
- Проверка. Прошёл `sh -n` всех трёх скриптов. На обычном файле вместо раздела проверены создание, список, отказ от перезаписи снимка, отказ при неверном размере, побайтное восстановление с вызовом заглушки перезагрузки и удаление. Запись и перезагрузка на R28S не выполнялись.

## 2026-11-25 — снапшоты FriendlyWrt на R28S

- Исследование. По SSH прочитаны разметка, параметры OverlayFS и штатный `firstboot`. Из копии раздела `boot` извлечён фактический initramfs. В его `scripts/local` подтверждены два маркера `.init_wipedata` и форматирование только `userdata` при обычном сбросе.
- Проектирование. Выбран gzip-образ полного раздела и ранняя обработка до монтирования, с проверяемым аварийным образом для прерванной записи. Точка интеграции локализована одним изменением `boot`. После Factory Reset отдельный скрипт возвращает автомонтирование и CLI.
- Реализация. Добавлены локальный упаковщик образа `boot`, статический обработчик и три скрипта. Штатный сетевой путь RouteCraft в этой работе не изменялся.
- Проверка сборки. `go test ./...` прошёл. Проверены побайтное восстановление тестового образа, отказ при повреждённом gzip или SHA-256, неверном размере, другой прошивке и незавершённом журнале ext4. ARM64-обработчик собран статически и найден в собранном из копии устройства `boot` с корректным KRNL CRC. Для проверки загрузки и аварийного отката нужен записываемый стенд R28S.
- Проверка на устройстве без записи. Штатная `sh -n` приняла три скрипта и изменённый `scripts/local`. Сравнение исходного и изменённого `scripts/local` подтвердило вызов перед проверкой суперблока. SHA-256 раздела `boot` на роутере совпал с сохранённым оригиналом.

## 2026-11-17 — причина потери WAN после reboot роутера

- Сделано: сопоставлен console output после reboot с прежними MAC-инвентаризациями. ## Первая установка на FriendlyWrt ARM64 — 2026-11-25

- Публичный архив прошёл SHA256, но сборщик распаковался без права исполнения. В текущей конфигурации устройства таблица 100 была пуста. Bootstrap теперь восстанавливает право исполнения перед запуском установщика. Проверку запуска из распакованного архива добавили в тест комплекта.
- На FriendlyWrt 25.12.5 в классической схеме исправленный bootstrap поставил недостающие пакеты из штатных feeds. После подключения системного Tailscale пользовательские файлы секретов дали реальную подписку и встроенный Exit Node. Подтверждены активация, автозапуск, LAN-правило policy routing, отсутствие однорукого NAT, `fw4 check` и локальный DNS. HTTPS через локальные SOCKS-входы подтвердил direct, реальный VLESS с отличным от direct внешним адресом и Tailscale. Отдельный LAN-клиент на этом устройстве не использовался. Установка оставлена активной.
- Если на первой установке рабочая VLESS-подписка отсутствует, мастер явно сообщает о продолжении без VLESS. При обновлении действует прежняя защита активной политики. На OpenWrt прошли проверка bootstrap для всех трёх архивов, сценарии подписки и первый кандидат без VPN.
## Штатный Split DNS по доменной политике — 2026-11-25

- Сборщик получает DNS-правила из используемой политики. Direct использует upstream мастера, VPN используют DNS по HTTPS через тот же выход. Настроенные вручную профили сохранены как переопределения. Для потока с известным именем применяются доменные фильтры в порядке политики. Для потока без имени работают условия по IP, порту и сети. Повторная установка сохраняет установленный `policy.yaml`.
- Первый реальный прогон подтвердил DNS через Tailscale и выявил неответивший VLESS-узел. DNS через него завершился тайм-аутом. Проверка DoH штатным `sing-box tools fetch` теперь выбирает ответивший узел до применения. Из-за влияния активной клиентской политики на загрузку геоданных GeoSite/GeoIP переведены на разрешение источника через upstream мастера.
- На выделенном классическом шлюзе bootstrap применил политику без секции `dns` и переключил dnsmasq. Проверены новый и повторный прогоны. С отдельного клиента прошли DNS по UDP/TCP, A/AAAA, HTTPS 200 с валидным TLS для `chatgpt.com`, `2ip.io`, `ifconfig.me` и `icanhazip.com`. Блокировка вернула `REFUSED`. Журнал подтвердил единый узел для DNS и HTTPS внутри каждого VPN-выхода. Конфигурация оставлена активной, SSH по системному Tailscale сохранён на обеих VM.
- Прошли Go-тесты, тесты подготовки подписки и проверки трёх архивов на OpenWrt. На аппаратных роутерах новая сборка не применялась.
