## Purpose / Big Picture

Сначала OpenWrt станет действующим шлюзом по умолчанию для тестового клиента: интернет-трафик клиента пойдёт через существующий исходящий шлюз OpenWrt и получит ответ. Затем простой sing-box распределит четыре тестовых назначения по правилам сверху вниз: одно через настоящую VLESS-подписку, одно через конкретный Tailscale Exit Node пользователя, одно напрямую и одно будет блокировано. Правильность подтверждается реальными запросами клиента и наблюдаемыми маршрутами. Это PoC на тестовых VM, без реализации дополнительных продуктовых механизмов.

## Surprises & Discoveries

Изменение только `net.ipv4.conf.all.src_valid_mark` с 0 на 1 на VM1 не воспроизвело проблему: клиентский HTTPS через VM1 вернул HTTP 200, хотя `ip route get` с mark и входящим интерфейсом вернул тот же `Invalid argument`, что и на пользовательском gateway. Этот эксперимент сам по себе не доказывал причину и противоречил более позднему изолированному воспроизведению. Значение sysctl и временный маршрут VM2 восстановлены.

Однократный тайм-аут VM2 при добавлении набора правил, похожих на системный Tailscale, не повторился при второй проверке. Эксперимент не доказывает причину. В журнале VM1 обнаружен трафик другого реального клиента, поэтому глобальные эксперименты на VM1 прекращены. Для изолированного воспроизведения на VM2 потребовался veth, который затем установлен с отдельного разрешения. С согласия пользователя выполнена точечная nft-трассировка на целевом gateway: запрос прошёл TPROXY и оставшиеся prerouting hooks с mark, но до input не дошёл; временная таблица удалена.

Позднее с отдельно разрешённым `kmod-veth` создана полностью изолированная топология на VM2. При исходном правиле запрос с реального клиентского namespace через sing-box прошёл при `src_valid_mark=0` и завис при `=1`; локальный HTTP-сервер и журнал inbound позволили отличить proxy от обхода. Ограничение policy rule входящим интерфейсом позволило запросу пройти в обоих режимах. Это опровергает ранний недостаточно изолированный эксперимент на VM1; причина заключается в обратной проверке маркированного пакета, а не доказана сообщением `ip route get` по отдельности.

Если прозрачный сокет недоступен, выражение nftables `tproxy` не выполняет оставшуюся часть своего правила. Исходная таблица разрешала пакету продолжить обычную пересылку; изолированный тест после остановки sing-box получил HTTP напрямую. Добавлен следующий за TPROXY явный drop для TCP/UDP; регрессия подтвердила прохождение TCP/UDP при работающем proxy и отказ обоих протоколов после его остановки.

При первом реальном тесте исправленных правил счётчик защитного drop вырос на неожиданных пакетах. Изолированная регрессия показала, что в таблице `inet` правило без ограничения семейства дополнительно блокировало IPv6. Условие `meta nfproto ipv4` устранило блокировку: IPv6 HTTP прошёл в отдельном стенде, а IPv4 fail-closed сохранился. Тестируемый продукт по-прежнему не реализует IPv6-маршрутизацию.

Опубликованный bundle содержал CRLF в нескольких shell-скриптах, хотя исходники рабочего дерева содержали LF: Windows-упаковка перенесла файлы из промежуточного Git-архива без нормализации. Предыдущая текстовая проверка сравнения скрывала различие переносов. Теперь упаковщик преобразует CRLF в LF и проверяет байты после извлечения созданного архива.

При первом `restart` отсутствующей службы OpenWrt сначала выполняет `stop_service`, затем procd вызывает `ubus call service delete` и сообщает `Not found`, после чего выполняется `start_service`. Воспроизведено на отдельной временной службе тестовой VM; формат ошибки в этой VM подробнее исходного сообщения пользователя.

На пользовательском gateway три локальных диагностических прокси возвращали HTTP-ответы, однако запросы транзитного клиента не доходили до TPROXY inbound sing-box, хотя счётчик nft увеличивался. `net.ipv4.conf.all.src_valid_mark=1`; обратный маршрут клиента с меткой RouteCraft указывал на local default через `lo` в таблице 100, без метки — на LAN. Маршрут с входящим интерфейсом и меткой возвращал `RTNETLINK answers: Invalid argument`. Это вероятная причина, но без контролируемого изменения маршрута и повторного теста она не доказана окончательно.

При разборе пользовательского теста обнаружены стендовые fallback-значения в нескольких частях установщика и отсутствие экспорта выбранных LAN-параметров дочерним скриптам. Передача параметров исправлена; собственно трафик после изменения не проверялся.

VM1 уже имеет `net.ipv4.ip_forward=1`, локальную подсеть `192.168.80.0/24` и маршрут по умолчанию через `192.168.80.254`; её `sing-box 1.13.21` собран с поддержкой Tailscale. Ранее на этих VM проверен отдельный временный TPROXY direct для TCP/UDP, но не работа шлюза по умолчанию с NAT и не выходы VLESS/Tailscale.

В актуальном MetaCubeX нет точных категорий `ru-blocked`; работающие SRS для GeoSite и GeoIP взяты из `runetfreedom/russia-v2ray-rules-dat`. Подписка содержала 13 совместимых VLESS-узлов. Один и тот же `chatgpt.com` встречается в категориях OpenAI и ru-blocked, что позволило проверить приоритет правила настоящим трафиком.

## Decision Log

- Решение: ограничить rule для метки RouteCraft входящим LAN-интерфейсом, а не отключать общесистемный `src_valid_mark`. Обоснование: reverse lookup выполняется как локальный запрос и не должен попадать в local-default RouteCraft; системная настройка остаётся доступной другим приложениям. Подтверждено изолированным TCP-тестом до и после изменения. 2026-11-14, Codex.
- Решение: при неудачной передаче в TPROXY отбрасывать клиентский TCP/UDP, а не пропускать к обычному forwarding. Обоснование: отсутствие socket не должно переключать VPN-политику на direct. Подтверждено изолированным тестом с остановленным sing-box. 2026-11-14, Codex.
- Решение: нормализовать shell-файлы на этапе сборки и проверять извлечённые архивы, а не полагаться на настройки Git или сравнение текстов. Обоснование: Windows может преобразовать окончания строк в промежуточном архиве независимо от рабочего дерева. 2026-11-14, Codex.
- Решение: если локальный Tailscale не использует Exit Node, предложить адрес только единственного узла с `ExitNodeOption=true`; при нескольких запросить выбор. Обоснование: реклама и разрешение узла не означают, что пользователь выбрал его среди нескольких вариантов. 2026-11-14, Codex.
- Решение: предлагать действующий ControlURL и только уже выбранный Exit Node из локального клиента Tailscale, если их удаётся прочитать; иначе использовать стандартный URL Tailscale и запросить Exit Node вручную. Обоснование: наличие узла в сети не означает, что пользователь выбрал его для выхода. 2026-11-14, Codex.
- Решение: ограничить работу двумя практическими ступенями: обычный IPv4 gateway с SRCNAT, затем четыре простых правила в sing-box. Обоснование: прямое уточнение пользователя; дополнительные системы и прежний план пока не исполняются. Дата/автор: 2026-11-13, Codex.
- Решение: тестовые «хосты» первой версии трактуются как четыре доменных назначения HTTP/HTTPS, задаваемые конкретными именами и проверяемые клиентом. Обоснование: пользователь просит сортировать пришедшие запросы по отдельным назначениям; адреса клиентов не зашиваются в правила маршрутизации продукта. Если фактический трафик не позволяет узнать имя, тест фиксирует это ограничение.
- Решение: использовать VM1 как шлюз, VM2 как клиент и штатный sing-box; не добавлять namespaces или новые службы без потребности. Обоснование: простота и доступность реальных тестовых устройств.

## Outcomes & Retrospective

Исправление сетевого пути и защиты от обхода опубликовано и доказано изолированными тестами на извлечённом bundle. На VM подтверждены реальные выходы Tailscale, VLESS, direct, reject и UDP DNS. После восстановления пользовательского gateway его штатная установка и те же реальные клиентские пути прошли при `src_valid_mark=1`. Проверка интерактивного ввода и перезагрузки этого устройства в последнем тесте не выполнялась.

Обновление мастера и bundles подготовлено; подбор текущего Tailscale клиента подтверждён изолированными сценариями, но не проверен с настоящим запущенным клиентом. Пользовательское устройство в ходе этого изменения не обновлялось.

Обе ступени PoC работают на тестовых VM. VM2 использует VM1 как шлюз; по пользовательской политике проверены Tailscale, VLESS и direct, а отдельное тестовое имя блокируется. ## Context and Orientation

Корень проекта `D:/Projects/github.com/vasiliy82/routecraft`. VM1 `root@192.168.80.241` — OpenWrt 25.12.6, интерфейс `br-lan`, default route через MikroTik `192.168.80.254`. VM2 `root@192.168.80.242` — тестовый клиент в той же подсети `/24`. SSH к обеим VM выполняется из этого окружения. Тестовые креды разрешено хранить в проекте, однако не выводить их без надобности.

SRCNAT — замена исходного адреса транзитного пакета адресом шлюза, чтобы ответ от `.254` вернулся через VM1. TPROXY — штатный Linux-механизм передачи транзитного TCP/UDP локальному sing-box с исходным назначением. `sing-box` уже доступен на VM1. Первый этап не зависит от TPROXY или VPN. Уровни DNS, geodata updater, LuCI, пакетирование, системы отката и прочие стадии старого плана вне этого PoC. Существующие незакоммиченные файлы не удалять и не переоформлять без необходимости.

Фактические результаты и ограничения внести в журнал. Параметры пользовательского gateway не менять в ходе изолированной отладки.

Сначала создать `poc/direct-gateway.sh` для VM1: включить IPv4 forwarding и добавить понятную таблицу nftables, которая делает masquerade транзитному трафику с LAN через тот же `br-lan` наружу. Существующий default route VM1 оставить через `.254`. Командой на VM2 выбрать `.241` как default gateway, сохранив локальную доступность по SSH. С VM2 сделать запрос к внешнему HTTP/HTTPS серверу, проверить default route и счётчик NAT; сравнить с запросом самой VM1. Результат и фактические команды внести в журнал. Скрипт должен сообщать об ошибке и не создавать дубли при повторном запуске.

После подтверждения прямого шлюза исследовать формат тестовой подписки и подготовить небольшой скрипт/конфигурацию в `poc/` для её VLESS-узла и отдельного Tailscale endpoint sing-box. По возможности использовать уже переданный рабочий прототип разбора подписки без создания дополнительного сервиса. Проверить `sing-box check` и отдельными прокси-запросами измерить фактические VLESS и Tailscale egress; попытка регистрации сама по себе не означает работающий Exit Node. Если exit node или подписка недоступны, продолжить независимую работу и честно описать конкретную ошибку.

Затем создать минимальную рабочую конфигурацию sing-box с TPROXY inbound, выходами direct, VLESS и Tailscale, и правилом reject. Задать четыре тестовых домена, проверить совпадение через sniff HTTP/TLS и сохранить порядок first-match; default direct. Включить принадлежащие PoC nftables и policy route для транзитных TCP/UDP, не перехватывая LAN, собственные соединения шлюза и управляющую сеть. Настроить доступ к DNS для VM2 так, чтобы тестовые имена разрешались. Проверить с VM2 четыре пути, а затем намеренно создать пересечение правил и переставить их местами: выбранный выход должен измениться. Для direct, VLESS и Tailscale фиксировать не только успешность запроса, но и наблюдаемый внешний IP/журнал соответствующего выхода, когда это доступно; для reject — отсутствие успешного ответа и журнал reject.

## Idempotence and Recovery

Скрипты затрагивают только названную таблицу PoC и тестовые VM; одинаковый запуск не должен создавать дубликаты. Не изменять физический роутер или другие устройства вне явно согласованной проверки. VM2 и VM1 остаются доступны по SSH по общей подсети. Если обычный интернет клиента нужно восстановить, его маршрут по умолчанию можно вернуть командой `ip route replace default via 192.168.80.254 dev br-lan`; пользователь предоставил снапшоты VM на случай более серьёзных проблем. Эта подсказка не вводит систему продуктовых откатов.
